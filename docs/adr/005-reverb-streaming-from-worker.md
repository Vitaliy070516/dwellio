# ADR-005: Reverb і стрімінг із воркера

- **Статус:** Прийнято (2026-11-26, рішення діє з Дня 6)
- **Контекст дня:** День 7, тиждень 1
- **Пов'язано:** `GenerateListingAd`, `AdStreamPublisher`, `ChunkBuffer`, `routes/channels.php`, ADR-002

## Контекст

Генерація оголошення триває 10–180 с. Користувач має бачити текст у міру появи, а не дивитися на спінер. Вимоги: HTTP-запит не тримає з'єднання з LLM; збій WebSocket не губить результат; приватність (без автентифікації користувачів у MVP).

## Порівняння

| Критерій | Воркер → Reverb (WebSocket) | SSE прямо з php-fpm | Polling `GET /listing-ads/{id}` |
|---|---|---|---|
| php-fpm воркер зайнятий на весь стрім | Ні, запит повертає `202` за мілісекунди | Так, до 3 хв — 10 користувачів з'їдають пул | Ні |
| Ретраї, DLQ, таймаути | Так, через чергу (ADR-002) | Ні: обрив браузера = обрив генерації | Так |
| Затримка до користувача | ~100 мс (батчі чанків) | Мінімальна | Інтервал опитування |
| Нові компоненти | Reverb (+ Redis pub/sub для кількох інстансів) | Немає | Немає |
| Горизонтальне масштабування | Reverb через Redis scaling | Разом із php-fpm | Тривіальне |

## Рішення

`POST /api/listings/{id}/ads` → запис `listing_ads` (queued) + Job у черзі `generation` → **202** з одноразовим токеном. Воркер стрімить LLM і публікує в приватний канал `private-listing-ads.{uuid}` події `ad.started` / `ad.chunk` (`attempt`, `seq`) / `ad.completed` / `ad.failed` через HTTP API Reverb (`ShouldBroadcastNow`, без другої черги). Авторизація каналу — guard `ad-token` (хеш токена в БД).

- **Джерело істини — БД, а не WebSocket.** Фінальний текст береться через `GET /api/listing-ads/{uuid}`; втрачений чанк нічого не ламає.
- **Батчі ~100 мс і ≤ 1000 символів** на повідомлення: кирилиця в JSON займає 6 байт/символ, ліміт повідомлення Reverb — 10 000 байт; ~10 повідомлень/с замість сотень.
- **Reverb недоступний → генерація триває**; після 3 невдалих broadcast поспіль стрім вимикається.
- `attempt` + `seq` дозволяють браузеру відкинути чанки старої спроби після ретраю.
- Reverb одразу зі scaling через Redis pub/sub: на тижні 4 досить збільшити `replicas`.

## Наслідки

**Плюси**
- HTTP-шар не залежить від тривалості генерації; ретраї й таймаути — у черзі.
- Деградація: без Reverb користувач отримає результат через GET.

**Мінуси і ризики**
- Ще один довгоживучий PHP-процес (Reverb): стежити за пам'яттю й кількістю з'єднань (тиждень 5, `[review]`).
- У scaling-повідомленнях Redis Reverb передає серіалізований `Application` **разом із secret** → Redis лише в приватній мережі й із паролем.
- Без автентифікації користувачів доступ тримається на секреті однієї генерації; втрачений токен = втрачений доступ (результат лишається в БД).

## Альтернативи, що відхилені

- **SSE з php-fpm.** Простіше, але кожен стрім займає воркер php-fpm до 3 хвилин і втрачає ретраї/DLQ.
- **Pusher / Ably.** Керований сервіс без ops, але платний після free-ліміту й зовнішня залежність; Reverb говорить тим самим протоколом, тож міграція — зміна конфігу.
- **Лише polling.** Найпростіше, але немає ефекту «текст пишеться на очах», і зайві запити до API.

## Умови перегляду

- > ~1000 одночасних WebSocket-з'єднань на інстанс — горизонтальне масштабування або керований сервіс.
- Якщо з'являться користувачі з сесіями — канал авторизувати за `user_id`, а не токеном генерації.
