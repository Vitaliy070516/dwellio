# ADR-003: pgvector + hybrid search (RRF)

- **Статус:** Прийнято (2026-11-26, рішення діє з Днів 3–5)
- **Контекст дня:** День 7, тиждень 1
- **Пов'язано:** `SearchListings`, `ParseSearchQuery`, міграції `listings` і `listing_embeddings`, ADR-001

## Контекст

Запит виглядає як «тихо, біля метро, можна з котом, до 20 тисяч». У ньому змішано:
- **жорсткі умови** (ціна, кімнати, район, тварини) — мають працювати як `WHERE`, а не як «схожість»;
- **м'які побажання** («тихо», «світла») — потребують семантики;
- **точні слова** (назва вулиці чи метро) — їх вектор часто губить.

Обсяг — сотні–тисячі квартир, один сервер, 1 ГБ RAM.

## Порівняння

| Критерій | pgvector у PostgreSQL | Qdrant / Weaviate | Elasticsearch / OpenSearch |
|---|---|---|---|
| Фільтри + вектор в одному запиті | Так, звичайний SQL | Так (payload filters) | Так |
| Синхронізація даних | Не потрібна: одна БД, одна транзакція | Потрібна (dual write / CDC) | Потрібна |
| Повнотекст для української | `simple` + `pg_trgm` (словника немає) | Слабко | Найкращий (аналізатори) |
| RAM / ops | 0 нових сервісів | +1 сервіс, ~0.5–1 ГБ | ≥ 1–2 ГБ heap — не влазить у `t3.micro` |
| Швидкість на мільйонах векторів | Добра з HNSW, гірша за спеціалізовані | Найкраща | Добра |

## Рішення

**PostgreSQL + pgvector**, три незалежні ранжування, злиті **Reciprocal Rank Fusion**:

1. **Вектор:** `listing_embeddings.embedding vector(1024)`, HNSW (`m = 16, ef_construction = 64`, cosine), фільтр за `embedding_model`.
2. **FTS:** GIN-індекс `to_tsvector('simple', title || ' ' || description)`.
3. **Trigram:** GIN `gin_trgm_ops` — ловить відмінки й одруківки, яких не бачить `simple`.

`score = Σ 1 / (k + rank)`, `k = 60`. RRF працює з позиціями, а не зі скорами, тому не треба нормалізувати несумісні шкали (cosine distance, `ts_rank`, similarity). Жорсткі фільтри застосовуються **в кожній гілці до ранжування**.

*Перевірено на Дні 9 (`search:eval`, 30 еталонних запитів):* `k = 60` і 50 кандидатів на гілку — на плато сітки `rrf_k` 1…100 × `candidates` 10…100 (коливання Recall ±0.02); кожна з трьох гілок дає релевантні результати, яких немає в інших.

LLM (Structured Output) розкладає запит на фільтри + семантичний залишок; її відповідь валідується як звичайний request. **Деградація замість помилки:** немає LLM або вичерпано бюджет → весь запит іде як текст; немає ембедингу → FTS + trigram; немає тексту → чисті SQL-фільтри. Розбір запиту й вектор запиту кешуються в Redis.

## Наслідки

**Плюси**
- Одна БД, одна транзакція, жодної синхронізації; бекап `pg_dump` покриває і дані, і вектори.
- Пошук не падає, коли падає AI: клієнт бачить `meta.mode` (`hybrid` / `text_only` / `filters_only`).

**Мінуси і ризики**
- **Розмірність зафіксована** в `vector(1024)`: локальна і прод-модель мусять збігатися; зміна моделі = міграція + `listings:reindex --all`.
- HNSW з фільтрами: при дуже селективних фільтрах індекс повертає замало кандидатів (post-filtering). Пом'якшення зараз — 50 кандидатів на гілку; далі — `hnsw.iterative_scan` (pgvector ≥ 0.8).
- Без морфології для української FTS слабший за Elasticsearch; семантику закриває вектор, відмінки — trigram.

## Альтернативи, що відхилені

- **Qdrant.** Швидший на мільйонах векторів, але +сервіс, +синхронізація і +RAM без потреби на нашому обсязі.
- **Лише вектор.** Губить точні умови («до 20 тисяч» перетворюється на «приблизно дешево»).
- **Зважена сума скорів.** Потребує нормалізації різних шкал і підбору ваг; RRF — без параметрів, крім `k`.

## Умови перегляду

- > 1–5 млн векторів або p95 векторної гілки > 100 мс на read replica.
- Потреба в морфології/синонімах української, яку не закривають вектор і trigram.
- При 100×: спершу RDS + read replica для пошуку, потім — окремий vector store.
